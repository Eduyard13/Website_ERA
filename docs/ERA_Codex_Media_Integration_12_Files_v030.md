# ЭРА — инструкция Codex: пилотная интеграция 12 медиафайлов на страницу «О проекте»

**Этап:** пилотное размещение уже подготовленных материалов, без общего редизайна.  
**Исходная версия сайта:** `0.30.0` (`https://eduyard13.github.io/Website_ERA/?v=0.30.0`).  
**Репозиторий:** `Eduyard13/Website_ERA`.  
**Страница:** `/` — «О проекте», концепция A «Ресурс».  
**Входные данные:** ZIP с файлами из таблицы ниже. Сам скриншот папки показывает имена и примерные размеры, но не гарантирует корректную структуру подпапок, кодеки или фактическое расширение файлов. **Проверить их после распаковки.**

## 0. Цель и границы работ

Интегрировать **ровно 12 уже собранных пользователем материалов** в предусмотренные на текущем сайте места. Получить рабочую, визуально аккуратную предварительную версию для просмотра и дальнейших правок.

Не менять утверждённую структуру восьми экранов главной страницы, не переставлять разделы, не включать режим «слайдов», не менять утверждённые тексты/смысл и базовую стилистику (индиго, золото, кремовые тона). Не редактировать технические показатели и финансовые модели. Не менять галерею, каталог, «Технологию», КАИР, «Экономику» и другие страницы, кроме неизбежных исправлений общих путей к ресурсам. **Существующую фотографию гранулы в карточке «Полный цикл» оставить без изменений.** Недостающие изображения для иных слотов сохраняют действующие резервные изображения.

Показатель **«до 80% засорённости сырья в испытаниях» — утверждённый результат ЭРА**, он уже предусмотрен на главной. Не убирать, не заменять его и не делать запрос на новый протокол. Производительность 1500 кг/ч смеси на входе и около 750 кг/ч очищенной плёнки относятся к расчётной конфигурации при засорённости около 50%; эти режимы не смешивать. Влажность — отдельный показатель.

**ВАЖНО:** архив — пользовательские медиа; никаких выдуманных материалов, стоковых замен, AI-генерации «реальных испытаний» или произвольной подмены изображений не требуется.

### Правила обработки нестандартных имён

1. Записи вида `hero/feedstock_hero.jpg.jpg` на скриншоте **могут быть как текстовыми именами в одной папке, так и путями в ZIP**. Не предполагать, что подпапки уже есть. Провести инвентаризацию содержимого архива: путь записи, базовое имя, размер, MIME/фактический формат, разрешение.
2. Для каждого файла создать реальные папки `hero/`, `process/`, `video/`, `products/`, `evidence/`, `system/`, `contact/` под `public/assets/project-home/`. Если слеши являются частью отображаемого имени — разобрать логический путь по первому `/`; если это реальные вложенные каталоги — просто сохранить их структуру при переносе.
3. Удалить **лишние промежуточные расширения**, но не изменять действительный формат: `*.jpg.png` означает проверку, затем сохранение в `.png`, если внутри PNG; `*.jpg.jpg` → `.jpg`, если внутри JPEG; `*.mp4.mp4` → `.mp4`, если внутри MP4.
4. **Запрещено** получить «JPEG» простым переименованием PNG. При необходимости сделать настоящую конвертацию. Следить за регистром имён на Linux/GitHub Pages.
5. Для публичного сайта предпочтительно автоматически подготовить оптимизированные WebP-версии фотографий (`hero/feedstock_hero.webp`, `process/preshredder.webp` и т. д.), сохраняя ожидаемые базовые имена. Резолвер `scripts/project-media.mjs` уже выбирает `*.webp`, `*.avif`, затем исходный формат. Не создавать дубли без необходимости.
6. Исходные тяжёлые файлы оставить в рабочем пользовательском архиве; в Git-репозиторий помещать только реально используемые веб-версии. Не увеличивать репозиторий ненужными копиями.

## 3. Композиция изображений по блокам

### A. Первый экран (без номера)

**Файл:** `hero/feedstock_hero` (производная WebP из JPEG).  
**Место:** крупное изображение загрязнённой плёнки в правой медиазоне существующего Hero. Не превращать его в задний фон всего экрана и не затемнять до потери фактуры сырья.  
**Формат:** на широком экране заполняет текущую правую визуальную колонку; допустимо аккуратное кадрирование `object-fit: cover`, только если не теряются главные детали материала. На мобильном — воспользоваться текущей адаптивной композицией, проверить видимость исходного материала.  
**Остальные элементы:** H1, подзаголовок, CTA и «до 80%» оставить, как в 0.30.0. Небольшой блок с оборудованием `heroEquipment` пока **не заменять** (отдельный файл ещё не передан). Не оставлять пустую рамку.

### B. Раздел 02 — три этапа обработки

**Файлы:** `process/preshredder`, `process/separator`, `process/clean_film`.  
**Место:** фото в верхней части трёх существующих карточек; одна карточка — один этап, без отдельной галереи.  
**Формат:** изображения оборудования показывать **целиком** насколько позволяет кадр: `object-fit: contain`, нейтральная фоновая подложка, единая высота медиаполей, без резкой обрезки корпуса, двигателя, транспортёра или рабочих органов. Не рисовать искусственно недостающие части.  
**Карточка 01:** пре-шредер → `preshredder`.  
**Карточка 02:** баллистический сепаратор → `separator`.  
**Карточка 03:** *двухчастная* иллюстрация остаётся: слева поставленная очищенная плёнка `cleanFilm`, справа **уже существующая фотография гранулы**, без изменений. Это показывает разницу между результатом сухой сепарации и полного цикла. Не создавать новый рисунок гранулы и не подменять очищенную плёнку гранулой.

### C. Раздел 02 — основной рекламный ролик

**Файл:** `video/era_promo_full.mp4`.  
**Место:** существующий блок `resource-promo` под технологическими карточками, с заголовком «ЭРА в действии: путь плёнки от отходов к новому сырью».  
**Формат:** один большой горизонтальный плеер 16:9, в рамках ширины контента (не fullscreen по умолчанию), с нормальным управлением, звуком, перемоткой и возможностью открыть на весь экран. На телефоне — ширина контейнера.  
**Поведение:** постер, крупный видимый Play/нативные элементы управления, загрузка по требованию (`preload="metadata"` или `none`), **без автозапуска и без автоматически включённого звука**. Не ставить этот тяжёлый видеопоток фоном Hero.  
**Постер:** поскольку отдельного JPG ещё нет, извлечь хороший чистый кадр непосредственно из ролика и создать `video/era_promo_poster.webp` (16:9), без чужих логотипов, чёрных полей, размытых движений и нечитаемых титров. Если в ролике нет подходящего кадра, временно использовать уже предусмотренный резервный постер; не блокировать запуск видео. Сохранять оригинальный монтаж и звуковую дорожку.

### D. Раздел 03 — два продукта

**Файл:** `products/clean_film_bale.jpg`.  
**Место:** левая карточка «Сухая сепарация» — крупная фотография готовой очищенной плёнки.  
**Формат:** горизонтальное верхнее изображение, `cover` без обрезания важной формы материала; плавный нижний градиент только для читаемости подписи.  
**Подпись:** если на фото не спрессованный тюк, писать **«Очищенная плёночная фракция»**, а не выдавать материал за тюк. Отделить этап сухой сепарации от мойки/грануляции.  
**Правая карточка:** существующая гранула **строго без замены и визуальной обработки**.

### E. Раздел 04 — демонстрация реальной работы и результатов

**Файлы:** `evidence/input_sample.jpg`, `evidence/process_running.jpg`, `evidence/output_sample.jpg`, `evidence/cleaning_demo.mp4`.  
**Место:** три равноправных фотокарточки горизонтальным рядом сверху: **«Сырьё» → «Оборудование в работе» → «Очищенная фракция»**. Это не слайдер, а наглядная последовательность. На мобильном — друг под другом, без микроминиатюр.  
**Кадрирование:** сохранять материал крупно, не допускать экстремальной потери качества или растягивания маленьких фото. Фотографии должны открываться в существующем просмотрщике.

**Подписи:** короткие фактические; если фото входа и выхода сняты в разных сериях, не создавать ложную подпись «одна партия до/после». Допустимо показать визуально последовательность технологических стадий, не утверждая неподтверждённой связи между кадрами. **Показатель 80% оставить заметным и утверждённым.**

**Подпись:** если материал является рендером/3D — **«3D-визуализация технологической линии ЭРА»**. Если реальная фотография — соответствующая фактическая подпись. Не путать визуализацию с фотографией работающего объекта.  
**Экран КАИР** заменить только после получения другого утверждённого файла; пока оставить существующий.

На мобильном держать кадр в правой/нижней периферийной области так, чтобы текст и кнопки оставались контрастными и читабельными; не перекрывать CTA, телефон и email. При необходимости только локально скорректировать `opacity`, `object-position`, `mask-image` для `.resource-contact-image`, без изменения глобального дизайна.

## 4. Видео: обязательная подготовка для GitHub Pages

Исходники со скриншота: `video/era_promo_full.mp4.mp4` — **около 220,2 МБ**; `evidence/cleaning_demo.mp4` — **около 105,8 МБ**. Эти объёмы неудобны для веб-страницы; обычный GitHub-репозиторий блокирует отдельные файлы свыше 100 МиБ. **Не пытаться коммитить исходники напрямую.**

1. Сначала проверить оба файла (`ffprobe` или эквивалент): длительность, разрешение, FPS, видеокодек, аудио, проблемы декодирования.
2. Создать веб-копии MP4 с H.264, `yuv420p`, AAC (если аудио есть), `-movflags +faststart` и адекватным битрейтом. Сохранить монтаж, титры, цвет, правильные пропорции, звук; **не ускорять, не вырезать и не заменять фрагменты**.
3. По возможности оставить 1080p. Ориентироваться на качество картинки на реальном плеере, а не только на размер; для тестовой версии **каждый файл должен быть ниже 90 МБ**, желательно заметно меньше, если удаётся без видимой деградации. При необходимости пробовать ступени качества/кодирования. Не менять расширение без реального перекодирования.
4. Плакаты (poster) — отдельные небольшие 16:9 WebP. Пользователь должен видеть привлекательный кадр **до** запуска видео. Убедиться, что плеер воспроизводится в Safari/Chrome и на мобильном.
5. Если без сильной потери качества уменьшить ролик не получается или в среде Codex отсутствует кодировщик, **не скрывать проблему**: подготовить изображения и остальные элементы, сообщить об ограничении и дать минимальный вариант подключения по отдельной видеоссылке после согласования. Не использовать Git LFS как способ автоматически обслуживать большие видео с GitHub Pages и не придумывать сторонний URL.
6. Оба ролика независимы; запуск одного не должен запускать другой. Не включать autoplay, не загружать целиком два видео до взаимодействия.

## 5. Оптимизация фото и техническая реализация

- На странице использовать оптимизированные форматы (в приоритете WebP), качественные JPEG/PNG как исходники только при необходимости; не ухудшать резкость реальных загрязнений и узлов и не подменять фото сгенерированными.
- Для основной фотографии Hero подготовить адаптивные размеры с шириной до ~1920–2200 px по исходному качеству, `srcset` и корректным `sizes`. Для остальных — уместные 480/880/1280/1920 px **только если исходное разрешение это позволяет**; маленькие фото не растягивать программно до фиктивных 1920 px.
- Для JPEG/PNG с ошибочным `.jpg.png` или `.jpg.jpg` проверить реальную сигнатуру файла. Включить правильные расширения и MIME в сборке.
