# ЭРА 0.50.0 на Reg.ru

## Подготовка в ispmanager

1. В меню сайта `era-cycle.ru` откройте «Менеджер файлов». Скопируйте из панели полный путь к каталогу `www/era-cycle.ru`. Создайте рядом с `www` каталоги `era-staging` для комплекта и `era-deploy` для закрытого состояния, если их ещё нет. Для `era-deploy` установите права `0700`.
2. Скачайте комплект и выполните `sha256sum -c SHA256SUMS`. Проверьте публичный ZIP командой `unzip -t ERA_SITE_PUBLIC.zip`. Загрузите комплект в `era-staging`. Резервную копию текущего сайта с действующими правами и защищёнными файлами сохраните вне всех публичных каталогов. Проверьте свободное место и возможность прочитать копию.
3. Возьмите манифест текущей установки из последнего подтверждённого релиза. Проверьте его на сервере. Пример ниже использует путь из панели и PHP 8.3 или новее. Если в комплекте имеется только предварительный `BEFORE.json`, используйте его как проверяемую гипотезу.

   ```sh
   ERA_WEB='/полный/путь/из/панели/www/era-cycle.ru'
   ERA_STAGE='/полный/путь/из/панели/era-staging'
   cd "$ERA_STAGE"
   php tools/regru_verify.php "$ERA_WEB" BEFORE.json
   ```

4. При `MISMATCH` найдите манифест фактически установленной версии, сверив историю установки и копию сайта. Если утверждённых хешей нет или в каталоге обнаружены неизвестные файлы, сохраните отчёт и запросите сверку перед обновлением. Для нового манифеста используйте только согласованные публичные пути. Закрытые файлы, пароли и SMTP-конфигурация для сверки не нужны.
5. Сверьте текущий HTML политики и согласия, редакции `ERA-PRIVACY-1.3` и `ERA-PD-1.3`, и их ссылки с предоставленным реестром совместимости. Сохраните текущий HTTP-ответ GET `/api/request.php`, курсы `/data/cbr.json`, статус HTTPS и редиректов. Промежуточный архив оставьте в `era-staging`.

## Подтверждённый патч

На рабочей машине с Python 3.11 или новее распакуйте публичный комплект в отдельный каталог. Создайте патч из этого каталога и проверенного манифеста. Подставьте полный SHA из `RELEASE_MANIFEST.json`.

```sh
mkdir -p payload
unzip -q ERA_SITE_PUBLIC.zip -d payload
python3 tools/regru_release.py prepare --dist payload --base BEFORE.json \
  --output reviewed --release 0.50.0 --commit "$ERA_RELEASE_COMMIT" --verified-baseline
(cd reviewed && sha256sum -c SHA256SUMS)
```

Сверьте `ADD`, `UPDATE` и `REMOVE_CANDIDATE`. Перед запуском проверьте, что в списке нет защищённых файлов и владелец утвердил SHA релиза. Загрузите новый патч и его манифесты в `era-staging/reviewed`.

### Применение через Shell-клиент

На хостинге используйте Python 3.11 или новее. Shell-команда применяет тот же алгоритм, что и действующий автоматизированный процесс.

```sh
cd "$ERA_STAGE"
php tools/regru_verify.php "$ERA_WEB" reviewed/BEFORE.json --record
python3 tools/regru_sync.py apply reviewed/ERA_UPDATE_0.50.0.zip \
  --local-web-root "$ERA_WEB" --receipt "$ERA_STAGE/LIVE_VERIFIED.json"
php tools/regru_verify.php "$ERA_WEB" RELEASE_MANIFEST.json
```

Обновление сначала проверяет старые версии затронутых файлов и сохраняет их копии. Новые ресурсы загружаются перед HTML. После передачи выполняется контроль HTTPS, страниц, курсов, PDF, MP4 и ответа API. При ошибке прочтите журнал и используйте `ROLLBACK.md`. Повтор успешного запуска передаёт 0 файлов.

При отсутствии Python на сервере используйте существующий процесс GitHub Actions с настроенным SFTP и отдельным подтверждением владельца. Порядок указан в [инструкции по подключению](ERA_REGRU_CONNECT.md). Для ручного обновления из панели распакуйте подтверждённый патч вне `www` и сохраните копии путей `UPDATE`. Передайте содержимое `files/` в порядке из `PLAN.json`, заменяя только перечисленные файлы. На входе и выходе используйте PHP-проверку. Порядок — новые ресурсы, обновлённые ресурсы, HTML, `robots.txt` и `sitemap.xml`. При ручном копировании веб-сервер может обслужить страницу во время передачи отдельного файла. Для сайта с активным трафиком используйте атомарную передачу через Shell или Actions.

Публичный архив содержит полный управляемый слой для существующего сайта. При выборе полного обновления объединяйте его с текущим содержимым через проверенный патч. Установленный PHP, два защищённых юридических HTML-файла и файл свежего курса нужны рабочему сайту и находятся на хостинге.

## Проверка после установки

1. Откройте главную, экономику, все четыре линии, документы, КАИР и контакты на компьютере и телефоне. В новом браузерном профиле проверьте отказ от карт, управление согласием в футере и открытие формы. Сверьте расчёт базового сценария 9,81 млн ₽ за 31 день и 112,93 млн ₽ за 365 дней.
2. Проверьте открытие исходных PDF и перемотку MP4. Убедитесь, что GET формы возвращает 405, данные ЦБ доступны и в форме действует редакция `ERA-PD-1.3`. Действующую отправку проверяйте в отдельно согласованном режиме. PHP, SMTP, CRON, .htaccess, загрузки пользователей и права доступа обслуживаются действующей серверной конфигурацией.
3. Запишите подтверждённое состояние отдельным манифестом после HTTP-проверок. Для последующих обновлений используйте именно его.
4. Подготовьте перечень устаревших файлов с помощью `regru_cleanup.py` и приложенного `browser-assets.json`. Выполняйте карантин после проверки работающей версии и периода кеширования прежних HTML/JS. Владелец утверждает конкретный SHA-256 плана. Подробности приведены в `REMOVE_CANDIDATES.md`.
