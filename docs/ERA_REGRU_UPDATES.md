# Как обновлять ЭРА

## Автоматизация после одного подключения

1. Откройте **Actions → ERA Reg.ru Prepare and approved deploy** для коммита из `deploy/regru`. В **Summary** проверьте список файлов, объём и результат тестов. Скопируйте номер запуска Prepare и полный SHA. Обычный push запускает только подготовку.
2. Одобрите именно этот патч командой ниже из репозитория. Подставьте номер успешного запуска и SHA из того же запуска. Если окружение `reg-ru` настроено с обязательным reviewer, подтвердите **Review deployments** для появившегося запуска.

   ```bash
   git tag regru-deploy-НОМЕР_ПОДГОТОВКИ ПОЛНЫЙ_SHA_ПРОВЕРЕННОГО_КОММИТА
   git push origin refs/tags/regru-deploy-НОМЕР_ПОДГОТОВКИ
   ```

3. Успешный запуск проверит HTTPS и запишет обновлённый манифест. Следующий Prepare сравнит новый результат с этим состоянием. Повтор без изменений показывает 0 файлов. Если нужна повторная подготовка для того же коммита после изменения базового манифеста, отправьте тег `regru-prepare-УНИКАЛЬНОЕ_ИМЯ` на этот коммит. Так не требуется добавлять workflow на `main`, где GitHub ищет определение для `workflow_dispatch`.

При неполном переносе сверяйте список `UPLOADED` и запись `era-deploy/transaction.json`. Повторно запустите тот же одобренный workflow. При ошибке контрольной проверки файлы отмечены как незавершённый релиз. Для отката этого релиза отправьте тег `regru-rollback-ПОЛНЫЙ_SHA` на тот же коммит. Восстановятся затронутые прежние файлы из проверенных копий. Новые файлы останутся отдельным списком на решение владельца. Если незавершённое соединение оставило `era-deploy/release.lock`, сначала сверьте активные запуски и состояние, затем удалите только пустой каталог блокировки вне `www`.

## ZIP-патч через ispmanager

1. В успешном **Prepare → Artifacts → era-regru-patch** скачайте материалы. Снаружи находится контейнер GitHub Actions, внутри — `ERA_UPDATE_<версия>.zip`, `SHA256SUMS`, `PATCH_MANIFEST.md`, `LIVE_AFTER.json` и инструкция. На компьютере проверьте `sha256sum -c SHA256SUMS` и `unzip -t ERA_UPDATE_<версия>.zip`.
2. В **Менеджер файлов** создайте `era-staging` рядом с `www`, вне всех публичных каталогов. Загрузите туда ZIP, распакуйте в отдельную папку, откройте `PATCH_MANIFEST.md`. До копирования проверьте `BEFORE.json` на сервере утилитой `regru_verify.php` из комплекта. Проверка читает хеши файлов на сервере и ничего не скачивает с него. Если найдены отличия, остановитесь и выясните происхождение изменений.

   ```text
   ПУТЬ_К_PHP_8_3 -f /ФАКТИЧЕСКИЙ_ПУТЬ/era-staging/regru_verify.php -- /ФАКТИЧЕСКИЙ_ПУТЬ/www/era-cycle.ru /ФАКТИЧЕСКИЙ_ПУТЬ/era-staging/patch/BEFORE.json
   ```

3. Сохраните резервные копии путей из `UPDATE` вне `www`, с их каталогами. Убедитесь, что пути `ADD` свободны. После своего подтверждения перенесите только содержимое `files/` по указанным относительным путям. Сначала CSS, JS, картинки и другие ресурсы, затем новые страницы и обновлённый HTML, в конце `robots.txt` и `sitemap.xml`. При копировании папок используйте слияние каталогов с заменой конкретных файлов из списка. Если панель предлагает заменить каталог целиком, скопируйте его указанные файлы отдельно. Архив, отчёт и манифесты оставьте в `era-staging`.
4. Проверьте главную, каталог, технологию, экономику, схемы, документы, четыре видео и их перемотку, валюту, HTTPS и редиректы, `robots.txt`, `sitemap.xml` и GET `/api/request.php` со статусом 405. Проверьте согласие и выбор карт в свежем браузере. Реальный POST выполняйте после юридического утверждения. Сверьте новое состояние `LIVE_AFTER.json` утилитой из шага 2. При ошибке верните только файлы `UPDATE` из копии в том же порядке. Новые пути выпишите для отдельного решения.
5. Если автоматизация уже подключена, после успешных проверок используйте `LIVE_AFTER.json` с `regru_verify.php --record`, затем запишите этот проверенный манифест на GitHub командой из инструкции подключения. Следующий отчёт будет исходить из обновлённого сайта.

Если на хостинге также доступен Python 3.11+, сайтом можно управлять локально по этому ZIP, используя `scripts/regru_sync.py`, `regru_release.py` и `regru_smoke.py` на сервере в `era-staging`. Это ручная команда владельца со сверенной базой и резервными копиями, выполняет тот же порядок и проверки. Перед запуском в `era-deploy/live-manifest.json` должна быть записана проверенная база из `BEFORE.json`.

```text
python3 regru_sync.py apply ERA_UPDATE_<версия>.zip --local-web-root /ФАКТИЧЕСКИЙ_ПУТЬ/www/era-cycle.ru --receipt /ФАКТИЧЕСКИЙ_ПУТЬ/era-deploy/last-verified.json
```

### Защищённые и отдельные выпуски

В обычной доставке охраняются `data/cbr.json`, `.htaccess`, `.well-known/`, остальные служебные каталоги, `privacy/index.html`, `privacy/consent/index.html`, `api/request.php`, всё `era-private/`, конфиг SMTP, журналы, исходники разработки и резервные копии. Кандидаты `REMOVE_CANDIDATE` требуют отдельного решения. При повторном подтверждении обычный патч не стирает их.

Редакцию политики и согласия оформляйте отдельной задачей. Укажите номер редакции, сравните публичные тексты с текущими, сделайте копии обоих файлов и примените правки контролируемо. Для серверного релиза отдельно согласуйте перечень публичного PHP и закрытых компонентов, совместимость, права файлов и порядок установки. Проверьте PHP 8.3, SMTP в контролируемой среде и HTTP GET 405 на сайте. Сохраняйте рабочий `era-private/config.json`, каталоги `state/` и журналы. Если меняется логика PDF, обработчика или согласия, синхронизируйте связанные файлы в этом отдельном выпуске.
